## 📊 向量数据库共用策略矩阵

### 1. 逻辑共用：一个服务，多个集合/索引

**定义**：一个向量数据库实例内创建多个不同的集合（Collection），数据物理隔离。

```
实例: Milvus/Qdrant/Weaviate
├── Collection: lingshu_l0_absolutes   # L0: 绝对事实/未解之谜
├── Collection: lingshu_l1_natural_laws # L1: 自然规律
├── Collection: lingshu_l2_individuals  # L2: 个体实情
└── Collection: lingshu_l3_consensus    # L3: 共识效用
```

**适用场景**：
- 公司内部多个项目共用一个数据库服务器
- 开发/测试环境节省资源

**优势**：
- 管理简单，资源复用
- 不同集合之间数据完全隔离

**局限**：
- 不能直接跨集合做联合检索
- 必须在应用层分别查询再合并结果

**在 LingShu 的应用**：
- L0-L3 各层使用独立 Collection
- 每层内部可进一步按时间、元胞规模分区

---

### 2. 物理共用：同一个集合，多租户

**方式一：字段分区（推荐）**

在集合 Schema 中增加 `tenant_id` 标量字段。

```python
# 示例：LingShu 的 L2 层个体数据
{
  "id": "uuid_here",
  "vector": [0.12, -0.08, ...],  # 384/768 dim embedding
  "tenant_id": "user_stardust",   # ← 租户标识
  "metadata": {
    "trit_state": "+1",
    "generation": 142,
    "personal_context": "初次观察有序态扩张"
  }
}

# 检索时
# WHERE tenant_id = 'user_stardust' AND vector SIMILAR TO query
```

**优点**：
- 标准方案，隔离性好
- 权限控制精确（可按 tenant_id 过滤）
- 所有主流向量数据库支持（Milvus, Qdrant, Weaviate）

**缺点**：
- 需要向量数据库支持标量过滤

**方式二：前缀区分 ID / 命名空间**

```python
# 不同租户的向量 ID 加前缀
ID格式: {tenant_prefix}_{entity_id}

# 示例
"stardust_l2_memory_001"
"hermes_l2_memory_001"
```

**优点**：
- 实现简单，无需 Schema 修改

**缺点**：
- 检索时必须精确知道 ID 范围
- 灵活性差，无法利用标量索引优化

---

### 3. 资源共用：小心性能干扰

即使逻辑上隔离，物理上仍共用 CPU、内存、磁盘 IO。

**风险**：
- **内存抢占**：一个业务把热门向量全加载进内存，导致其他集合查询变慢
- **写入冲突**：A 大批量导数据时，B 的查询延迟飙升

**缓解措施**：
- 资源配额（QPS 限制、内存上限）
- 读写分离（热副本用于查询）
- 时间窗口调度（批量写入放在低峰期）

---

### 4. 不建议共用的情况

| 场景 | 建议 |
|------|------|
| 安全合规要求极高（医疗、金融） | **物理隔离实例** |
| 核心交易链路 vs 内部测试工具 | **K8s 独立 Pod 资源组** |
| SaaS 软件给不同客户 | **字段分区 + 严格 tenant_id 过滤** |

```python
from sentence_transformers import SentenceTransformer

class TritEmbedder:
    """将三态序列编码为向量"""
    
    def __init__(self):
        self.model = SentenceTransformer('all-MiniLM-L6-v2')
    
    def trit_sequence_to_vector(self, trits: List[int]) -> List[float]:
        """将 [-1, 0, 1] 序列转为语义向量"""
        text = self._trit_to_text(trits)
        return self.model.encode(text).tolist()
    
    def _trit_to_text(self, trits: List[int]) -> str:
        # +1 → "有序"
        # 0 → "沉默"
        # -1 → "混乱"
        mapping = {1: "有序", 0: "沉默", -1: "混乱"}
        return ''.join(mapping[t] for t in trits)
```

## 📚 附录：向量数据库基础

### 什么是向量数据库？

传统数据库存储**结构化数据**（数字、字符串、日期），而向量数据库存储**向量（数组）**，用于：

1. **语义搜索**："猫"的向量 ≈ "猫咪"的向量
2. **相似推荐**：喜欢 A 电影 → 推荐向量相近的 B 电影
3. **模式识别**：在演化历史中检索相似的元胞状态 pattern

### 向量化过程

```
文本/图像 → 嵌入模型 → 向量 (384/768/1536 维)
           (BERT, CLIP, 等)
```

在 LingShu 中：
```
三态序列 [-1,0,1,-1,...] → TritEmbedder → 向量 → 向量数据库
```

### 检索过程

```
查询向量 q
    ↓
在向量库中找 top-k 最相似向量（余弦相似度）
    ↓
返回对应的元数据（原始状态、时间戳、租户信息）
```

## 🎯 与 L0-L3 架构的对齐

| 认知层 | 向量数据库角色 | 共用策略 |
|--------|---------------|---------|
| **L0** | 不存储，只存哈希指针 | 无需共用 |
| **L1** | 只读规则库，所有租户共享 | 全局只读 Collection |
| **L2** | 个体记忆，严格隔离 | 字段分区（tenant_id） |
| **L3** | 动态共识，实时更新 | 全局写入 + 版本追踪 |

**共用结论**：
- **L1** 层：完全共用（同一份自然律）
- **L2** 层：逻辑隔离（租户字段过滤），物理可共用同一实例
- **L3** 层：完全共用（共识本应公开）
- **L0** 层：不进入向量库

## 📋 总结

1. **向量数据库可以共用**，但需明确共用层级
2. **推荐字段分区方案**（tenant_id），平衡隔离与成本
3. **LingShu 存储架构**应与 L0-L3 认知层严格对齐
4. **P1 阶段先用 PostgreSQL + pgvector** 验证逻辑，P2 迁移到专用向量库
5. **多智能体协作**时，L2 个体数据必须非侵害隔离，L1/L3 可共享
